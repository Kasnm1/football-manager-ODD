# FMODD 前端生成与界面秩序规范

> 状态：当前规范
> 适用范围：`web/index.html`、`web/app.css`、`web/dark-theme.css`、`web/app.js` 中新增或修改的用户界面
> 目的：让 FMODD 的功能增长保持统一、可识别，并避免回到通用 AI Dashboard 风格。

## 1. 产品视觉主张

FMODD 是 Football Manager 的本地俱乐部工作台，核心体验是读取、比较、判断和执行足球数据操作。

前端应当接近：

- Football Manager 的管理工具
- 体育数据终端
- 有明确足球语义的桌面应用

前端不应当接近：

- 通用 SaaS 仪表盘
- AI 产品落地页
- 电商卡片墙
- 只展示功能而不帮助用户完成工作的视觉稿

个性化来自信息组织、足球语义、数据密度和稳定的交互习惯，不来自装饰数量。

## 2. 绝对规则

新增界面默认禁止以下模式；只有明确的业务语义和书面理由才能例外：

- “图标 + 标题 + 说明 + 按钮”作为所有功能的默认结构
- 三列或四列等宽卡片墙
- 每个容器都加阴影、渐变或玻璃模糊
- 装饰性图标圆 pill、无意义徽章、悬浮按钮
- 标题或卡片左侧的装饰性强调边线
- 所有元素使用同一个大圆角
- 用超粗字重、渐变文字或发光效果制造层级
- 用颜色代替文字、位置或形状表达状态
- 为了“看起来丰富”增加没有信息含义的图形

尤其不要把新的页面机械套入现有卡片模板。先决定用户要完成什么，再决定容器。

## 3. 信息层级

每个页面和组件都按以下顺序组织：

1. 用户当前要完成的动作
2. 完成动作所需的主数据
3. 状态、时间、来源和限制
4. 次要说明、帮助和恢复操作

标题不重复说明文字。只有用户不能从界面推断出的风险、限制、等待或恢复信息才显示说明。

数字、赔率、比分、日期和球队名优先于装饰性标题。

## 4. 布局选择

| 内容性质 | 首选结构 | 不要默认使用 |
| --- | --- | --- |
| 赛程、积分、球员、职员、历史记录 | 表格或紧凑数据行 | 信息卡片墙 |
| 赔率选项 | 分组盘口面板、横向选项行 | 每个选项一张独立卡片 |
| 投注单、复杂表单、独立数据块 | 面板或有限数量的卡片 | 嵌套卡片 |
| 筛选和批量操作 | 工具栏 | 分散在多个卡片底部的按钮 |
| 短确认、少量输入 | 弹窗 | 用弹窗承载完整页面 |
| 需要持续对照的内容 | 同屏双栏或表格 | 藏在多层 Tabs 里 |
| 真实空间关系（球场、训练位置） | 空间布局 | 为了装饰而使用空间图 |

等宽列只有在数据确实同等重要时才使用。大多数页面应有明确的主列和辅助列。

## 5. ODD 的基础视觉语言

### 字体

当前基础字体栈为（可在“设置 → 显示”中为当前界面语言选择字体）：

```css
var(--fmodd-locale-font), var(--fmodd-english-font), var(--fmodd-chinese-font), sans-serif
```

字体设置按界面语言保存在本机 `localStorage`，切换语言不会覆盖其他语言的选择。简体中文、繁体中文、韩语和日语界面同时显示两组选项：当前 CJK 文字系统的字体，以及共用的英文字母与数字字体；渲染时限制拉丁字体优先覆盖 Latin、数字和常用符号，CJK 字形继续由当前语言字体承担。其他语言只显示当前界面语言的字体选项。简体中文默认 `Microsoft YaHei UI`，繁体中文默认 `Microsoft JhengHei`，韩语默认 `Malgun Gothic`，日语默认 `Yu Gothic UI`，英文、德语、西语、法语和俄语默认 `Segoe UI`；各自下拉框只列出适合该文字系统的常见 Windows 字体及明确的 Noto/Source Han 回退候选。未安装字体由系统字体栈回退，不改变存档数据。旧版简体中文和英文的本地字体偏好会迁移到对应语言，CJK 混排中的拉丁字体沿用英文偏好。设置另提供六档字号滑块（默认第三档）。

界面语言支持 English、简体中文、繁體中文、한국어、Deutsch、Español、Français、Русский、日本語、Português (Brasil) 与 Português (Portugal)。全新安装默认英文，升级前已存在但没有语言字段的设置保持简体中文；语言切换在当前页面原地生效，不刷新页面、不清空投注选择或未提交输入。英文是缺失翻译的统一回退，球队、球员、自定义名称和其他游戏事实不做通用翻译。

规则：

- 用户可见文字不得小于 `13px`
- 正文通常使用 400–500
- 标题通常使用 600–700
- 800/900 只用于确实需要强调的比分、赔率、结果或品牌标记
- 持续变化的数字使用 `font-variant-numeric: tabular-nums`
- 不为单个页面随意引入新字体；如需品牌字体，必须说明作用范围和回退字体

### 颜色

- 绿色是 ODD 的主要行动和正向状态色
- 金色只表示重要性、荣誉、选中或稀缺资源，不作为装饰线填满页面
- 红色表示风险、失败或损失
- 灰色和背景色负责分组，不要让每个模块都拥有独立的高饱和颜色
- 状态不能只靠颜色表达，必须同时有文字、图标、位置或形状

### 边框、圆角和阴影

- 结构性表格、导航和数据行优先使用分隔线或留白
- 输入和紧凑按钮使用小圆角（约 3–5px）
- 普通面板使用中等圆角（约 6–8px）
- 大圆角只用于真正的特色场景，不作为全局默认
- 阴影只表示真实的层级关系；平面内容不要用阴影强行分组
- 不使用装饰性左边线、霓虹边框或彩色光晕

## 6. 组件规则

### 导航

导航首先保证名称、顺序和当前状态清楚。图标是辅助信息，不得代替文字，也不应每个入口都为了“完整”强行配图标。

### 工具栏

工具栏集中筛选、范围、刷新和批量操作。控件按操作顺序排列，避免一个页面出现多个互相竞争的主按钮。

### 页面标题

标题只回答“这里是什么”。当前范围、连接状态、更新时间和危险提示放在标题旁边或下方，不要堆成营销式副标题。

### 数据行

数据行应保持列对齐、数字稳定和快速扫描。优先使用轻分隔线、交替背景或选中背景表达层级，不要给每一行套一张卡片。

### 按钮

- 主按钮：一个页面或一个明确工作区最多一个主要动作
- 次按钮：描边或低对比背景
- 文字操作：用于低风险、可逆或辅助动作
- 危险操作：明确写出动作，不使用只有图标的危险按钮
- 图标按钮必须有可访问名称和可见焦点状态

### 空、忙、错和恢复状态

每个新数据区都要考虑：加载中、空结果、错误、忙碌、选中、禁用和恢复。不要用全屏 spinner 掩盖一个局部查询，也不要吞掉错误原因。

## 7. ODD 页面个性化边界

共享基础规则，但不同页面要保留自己的工作语义：

- 投注：赛程行、盘口分组、赔率选择和投注单是主结构
- 积分榜：表头、排名、状态和调整记录是主结构；不得仅凭固定名次区间渲染冠军、晋级或降级颜色，玩家执教球队可保留身份高亮；页面右上角的手动刷新调用积分榜刷新入口并复用共享刷新忙碌状态，刷新中禁用并公开 `aria-busy`
- 球队/球员：紧凑身份摘要 + 可扫描的数据列表
- 训练场：只有位置和空间关系是真实需求时才使用球场布局
- 银行/商店：金额、成本、限制和结果优先于商品卡片装饰
- 名人堂：可以使用更有历史感的字体和材质，但不得改变基础可读性和状态语义

如果一个新页面可以原封不动地改名为“CRM、AI SaaS 或银行后台”，说明它还没有体现 ODD 的领域语义。

## 8. 前端生成协议

任何新增或重做前端内容，在写代码前先写出以下五项（可放在任务说明、PR 描述或实现注释中）：

1. 页面工作：用户在这里要完成什么？
2. 主数据：用户第一眼必须看到什么？
3. 布局选择：为什么使用表格、列表、面板或卡片？
4. ODD 特征：这个页面通过什么足球语义与其他工具区分？
5. 禁止动作：本页明确不使用哪些通用模板手法？

实现时优先复用现有变量和组件。新增颜色、字体、圆角、阴影或动画时，必须能说明其业务作用。

## 9. 交付前检查清单

- [ ] 页面主要动作是否明显且只有一个主路径？
- [ ] 主数据是否比装饰性标题更突出？
- [ ] 是否不必要地把内容包装成卡片？
- [ ] 是否出现了图标 + 标题 + 说明 + 按钮的重复模板？
- [ ] 是否出现无语义的渐变、阴影、徽章、圆角或边线？
- [ ] 表格和数字是否容易扫描、对齐且使用稳定数字宽度？
- [ ] 选中、忙碌、错误和禁用状态是否清楚并可恢复？
- [ ] 深色主题、键盘焦点和最小字号是否保持一致？
- [ ] 页面是否有明确的 FM/足球工作语义？
- [ ] 如果去掉所有图标和装饰，信息结构是否仍然成立？

这份规范是当前前端生成的长期基线。设计研究、截图参考和一次性迭代记录不能替代它；若长期规则改变，应直接更新本文件并说明变更原因。
